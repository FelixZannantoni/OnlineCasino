# AI Agent Documentation

## Overview

This document provides guidelines and standards for AI agents and LLM-based tools interacting with the OnlineCasino codebase. The purpose is to ensure consistent, correct, and maintainable behavior when AI agents work with this codebase.

> **Note on scope of "casino" terminology**: This application uses simulated, virtual chips with no real-money value, purchase, cash-out, or withdrawal functionality. Nothing in this codebase should be treated as, or extended to become, real-money gambling infrastructure. Where this document mentions "balance," "chips," or "bets," these always refer to virtual, non-redeemable currency. If a request would introduce real payments, real currency exchange, or real-money withdrawal, treat it as out of scope and flag it to the user rather than implementing it.

## Agent Core Purpose and Scope

### Purpose
The primary purpose of AI agents working with this codebase is to assist in development, testing, documentation, and maintenance of the OnlineCasino web application. The agent should help human developers by:
- Implementing features according to specifications
- Writing and maintaining code
- Running tests and verifying changes
- Updating documentation
- Debugging issues

### Scope

#### What the Agent Should Do:
- Implement new features for backend games (Blackjack, Poker, Roulette, Slot Machine)
- Create and maintain frontend components and services
- Write and update API routes and services
- Generate unit tests for game logic and services
- Maintain documentation (README, AGENTS.md, etc.)
- Review and refactor code for maintainability
- Debug issues reported in GitHub issues
- Ensure code follows TypeScript, Angular, and project conventions

#### What the Agent Should NOT Do:
- **Directly access or modify production databases** - use the isolated test database only (see Data Sources)
- **Commit secrets, API keys, or sensitive credentials** to the repository
- **Modify user accounts, balances, or game state in production**
- **Make changes to the frontend without corresponding backend changes** when needed
- **Skip testing or validation before committing code**
- **Modify configuration files that require manual approval** (.env, docker-compose.yml for production)
- **Break existing functionality** without thorough testing
- **Implement any real-money payment, deposit, or withdrawal functionality**

### Boundaries of Responsibility

1. **Backend Development**: Agent may implement game logic, services, and API routes
2. **Frontend Development**: Agent may implement Angular components, services, and styling
3. **Testing**: Agent may write and run tests for frontend and backend code
4. **Documentation**: Agent may update project documentation
5. **Code Review**: Agent may provide code review suggestions (not formal review)
6. **Database Operations**: Agent may query test data only
7. **Deployment**: Agent should NOT deploy code without human approval

## Environment Setup

### Prerequisites
- **Node.js**: v20.x LTS or higher (required for Angular v20+ and Express v5.x)
- **Package manager**: npm (v10+, bundled with Node 20)

### First-Time Setup
```bash
# Backend
cd backend
npm install
cp .env.example .env   # if present; otherwise create .env with PORT=3000
npm run dev             # or: npm start, depending on package.json scripts

# Frontend (separate terminal)
cd frontend
npm install
ng serve                 # runs on http://localhost:4200 by default, proxies API calls to backend
```

- The backend listens on the port defined by `PORT` in `.env` (default `3000`).
- The frontend dev server expects the backend to be running and reachable; check for a `proxy.conf.json` in `frontend/` for how API calls are routed in development.
- The SQLite database file (`backend/resources/db.db`) is created automatically on first run if it doesn't exist, seeded with default test data.

### Running Both Together
Use two terminal sessions (or a process manager/`concurrently` script if one is configured in the root `package.json`). Confirm actual scripts in each `package.json` before assuming the commands above are exact — they may differ from this generic guidance.

## System Prompts and Behavioral Constraints

### General Principles

- **Transparency**: Always inform the user when taking actions that modify code
- **Safety First**: Never modify code that could negatively impact user accounts, financial data, or production systems
- **Test Thoroughly**: Always run relevant tests before confirming code is working
- **Follow Conventions**: Match existing code style, naming conventions, and architecture patterns
- **No Assumptions**: Don't assume user account data exists - check first and create if needed
- **Security Conscious**: Use secure practices (hashing, input validation, error handling)

### Tone and Style

- **Direct and concise**: Clear communication without unnecessary elaboration
- **Helpful**: Provide actionable information and guidance
- **Professional**: Maintain professional tone throughout interactions
- **Educational**: When explaining concepts, use clear examples

### Decision-Making Guidelines

- When implementing features, check existing code first and follow patterns used there
- If unsure about requirements, ask the user for clarification
- Prefer minimal, focused changes that address the specific issue
- When multiple solutions exist, choose the one that best matches existing code patterns
- Always validate input and validate game logic before rendering results
- Use proper error handling and user-friendly error messages

### Escalation Path

If the agent discovers something during a task that goes beyond the immediate scope of the request — for example, a security vulnerability, credentials or secrets already committed to the repository, evidence of database corruption, or a change that would affect production — it should:

1. **Stop before proceeding further** with the original task if continuing would compound the issue.
2. **Report the finding clearly to the user**, including what was found, where, and why it's a concern.
3. **Not attempt to silently fix, hide, or work around** the issue (e.g., do not delete evidence of a committed secret without telling the user — rotating/removing secrets has implications beyond the repo).
4. **Wait for explicit direction** before taking remedial action, unless the fix is trivial, obviously safe, and within the original scope (e.g., adding a missing input validation check).

### Restrictions

1. **No Direct Database Access**: Never write to the main database without explicit user approval
2. **No Production Changes**: All changes should be made in development/test environments
3. **No Sensitive Data Handling**: Do not process or store actual credit card numbers, real money transactions, or personal financial data
4. **No Arbitrary Code Execution**: Never execute unknown shell commands or remote code
5. **No Overwriting Code Without Backup**: If making significant changes, suggest the user create a backup first

### Real-Time Architecture (Socket.io)

Poker, and potentially other multiplayer-facing features, rely on Socket.io for real-time state synchronization between players and the server. When working on real-time features, the agent should confirm the following in the actual code before making changes, since this is not fully standardized yet:

- **Room/namespace structure**: which socket rooms or namespaces represent a given game table or session, and how clients join/leave them
- **Event naming conventions**: check `backend/src/gameLogic/poker/` (or equivalent) and the frontend socket service for existing event names before introducing new ones — keep event names consistent (e.g., `game:update`, `player:action`) rather than inventing a new convention per feature
- **Server as source of truth**: game state changes should be validated and broadcast from the server; the client should never apply an optimistic state change to a shared game without server confirmation
- **Disconnect/reconnect handling**: verify how a player's disconnect is currently detected (socket `disconnect` event, heartbeat, timeout) and how "auto-fold on leave" is actually implemented before assuming it works as described in the Error-Handling section
- **Testing real-time code**: prefer testing socket event handlers in isolation (mock the socket) over requiring a live multi-client setup, where feasible

If the agent cannot find an existing pattern for a piece of real-time behavior described elsewhere in this document (e.g., "Player leaves mid-game → Auto-fold with minimum loss"), it should treat that as a spec to implement or verify, not as guaranteed existing behavior.

### Authentication & Sessions

Before modifying any auth-related code, the agent should confirm the actual mechanism in use by reading `backend/src/services/user-service.ts` (or equivalent) and the relevant router — do not assume a specific scheme. At minimum, check and document:

- Whether sessions are JWT-based, cookie-based, or another mechanism
- Where/how the token or session identifier is issued (on `/users/login`) and validated (middleware)
- Token/session expiry duration and what "re-authenticate on expiry" means concretely on both frontend and backend
- How `UNAUTHORIZED` errors are triggered and distinguished from `INVALID_CREDENTIALS`

#### Frontend Coding Standards

These conventions are enforced project-wide (see `frontend/CLAUDE.md`) and MUST be followed when the agent writes or edits Angular code:

**TypeScript:**
- Use strict type checking
- Prefer type inference when the type is obvious
- Avoid the `any` type; use `unknown` when the type is uncertain

**Angular:**
- Always use standalone components — do NOT use NgModules
- Do NOT set `standalone: true` in the `@Component` decorator; it's the default in Angular v20+
- Use signals for state management
- Implement lazy loading for feature routes
- Do NOT use `@HostBinding` or `@HostListener` — put host bindings in the `host` object of the `@Component`/`@Directive` decorator instead
- Use `NgOptimizedImage` for all static images (does not work for inline base64 images)

**Accessibility:**
- Code MUST pass all AXE checks
- Code MUST meet WCAG AA minimums, including focus management, color contrast, and ARIA attributes
- If no automated AXE check is wired into CI yet, run `axe-core` (or the Angular CDK a11y testing utilities) manually against changed components before considering accessibility work complete — do not assume a CI gate catches this

**Components:**
- Keep components small and single-responsibility
- Use `input()` and `output()` functions instead of decorators
- Use `computed()` for derived state
- Set `changeDetection: ChangeDetectionStrategy.OnPush`
- Prefer inline templates for small components
- Prefer Reactive forms over template-driven forms
- Do NOT use `ngClass`/`ngStyle` — use `class`/`style` bindings instead
- External template/style paths must be relative to the component's TS file

**State Management:**
- Use signals for local component state
- Use `computed()` for derived state
- Keep state transformations pure and predictable
- Do NOT use `mutate` on signals — use `update()` or `set()` instead

**Templates:**
- Keep templates simple; avoid complex logic
- Use native control flow (`@if`, `@for`, `@switch`) instead of `*ngIf`, `*ngFor`, `*ngSwitch`
- Use the async pipe for observables
- Do not assume globals like `new Date()` are available in templates
- Do not write arrow functions in templates (unsupported)

**Services:**
- Design services around a single responsibility
- Use `providedIn: 'root'` for singleton services
- Use the `inject()` function instead of constructor injection

If no test-database setup currently exists in the codebase, treat creating one as a prerequisite task rather than assuming it's already in place.

Combined with Socket.io's concurrent, event-driven nature, this means balance updates and game-state writes must be carefully sequenced (e.g., within a single synchronous transaction) to avoid race conditions — do not assume Node's single-threadedness alone prevents interleaved reads/writes across concurrent socket events.

## Version Control & Contribution Workflow

Since this codebase is under active agent-assisted development, the agent should follow these conventions unless the user specifies otherwise:

- **Branching**: Create a feature branch per task (e.g., `feature/roulette-double-zero`, `fix/blackjack-split-bug`); do not commit directly to `main`/`master` unless the user explicitly asks for it or the repo has no branch protection and the user has indicated direct commits are fine.
- **Commits**: Write clear, scoped commit messages describing what changed and why (e.g., `fix: correct blackjack split payout calculation`). Avoid bundling unrelated changes into one commit.
- **Pull requests**: Prefer opening a PR for review rather than merging directly, especially for anything touching game logic, balances, or auth. Summarize the change, testing performed, and any follow-up needed in the PR description.
- **Human approval gate**: Regardless of branch/PR conventions, changes affecting production configuration, deployment, or real user data always require explicit human approval before merging — this is not optional based on branching strategy.

## Expected Input/Output Formats and Error-Handling Protocols

### Request Formats

#### HTTP API Requests

**Standard Response Format:**
```typescript
{
  success: boolean
  data?: any // Response payload
  error?: {
    code: string
    message: string
  }
}
```

**Example User Login:**
```json
POST /users/login
{
  "email": "player@example.com",
  "password": "securePassword123"
}

Response:
{
  "success": true,
  "data": {
    "uuid": "user-uuid-here",
    "userName": "player1",
    "displayName": "SuperPlayer",
    "balance": 1000,
    "streakCount": 0
  }
}
```

#### Game Requests

**Blackjack Example:**
```json
POST /blackjack/start
{
  "userId": "user-uuid",
  "bet": 100
}

Response:
{
  "success": true,
  "data": {
    "gameId": "game-uuid",
    "deck": [...],
    "playerHand": [...],
    "dealerHand": [...],
    "currentBet": 100,
    "balanceAfterBet": 900
  }
}
```

### Response Formats

#### Success Responses:
- Always include `success: true`
- Include relevant `data` payload
- HTTP status: `200 OK` or `201 Created`

#### Error Responses:
```json
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Player does not have enough chips to place this bet"
  }
}
```

#### Common Error Codes:
- `INSUFFICIENT_BALANCE` - User doesn't have chips for bet
- `INVALID_BET` - Bet amount outside valid range
- `GAME_NOT_FOUND` - Requested game doesn't exist or hasn't started
- `UNAUTHORIZED` - Authentication token missing or invalid
- `USER_NOT_FOUND` - User account doesn't exist
- `DUPLICATE_EMAIL` - Email already registered
- `INVALID_CREDENTIALS` - Incorrect email/password combination
- `GAME_OVER` - Game state changed (should restart)
- `INVALID_MOVE` - Illegal move for current game state
- `INSUFFICIENT_FUNDS_FOR_PURCHASE` - User doesn't have enough chips to buy a cosmetic item
- `ITEM_ALREADY_OWNED` - User attempted to purchase a cosmetic they already own
- `ITEM_NOT_FOUND` - Requested cosmetic ID doesn't exist

### Error-Handling Protocols

#### Server-Side:
1. Validate all inputs (user input, bet amounts, game moves)
2. Check game state consistency (can player afford bet? is game ready?)
3. Use appropriate HTTP status codes:
   - `400 Bad Request` - Invalid input or game state
   - `401 Unauthorized` - Authentication issues
   - `403 Forbidden` - Insufficient permissions
   - `404 Not Found` - Resource doesn't exist
   - `500 Internal Server Error` - Unexpected errors
4. Return descriptive error messages in JSON format
5. Log errors with full context (user ID, game ID, request details)
6. NEVER expose stack traces to client for security reasons

#### Game Logic Error Handling:
- **Deck Management**: Ensure deck is properly shuffled and cards are removed
- **Balance Updates**: Use atomic operations to prevent race conditions
- **Session State**: Use server-side game state to prevent client-side cheating
- **Round Outcomes**: Clear round state after resolution, even on errors
- **Connection Issues**: Persist round state on server until round completes

#### Client-Side:
1. Display user-friendly error messages from API responses
2. Retry failed requests with appropriate backoff
3. Clear game state if server confirms game is over
4. Re-authenticate user if session token expires
5. Log errors for debugging (without exposing sensitive data)

### Game-Specific Error Scenarios

#### Blackjack:
- Insufficient chips for bet → Block game start, show alert
- Invalid move (hit on blackjack, split on two-card hand) → Show error message
- Network timeout during move → Show loading state, timeout after N seconds
- Deck ran out of cards → Auto-resolve game, notify user

#### Poker:
- Fold without enough chips → Block fold, show warning
- Invalid raise amount → Block raise, show error
- Player leaves mid-game → Auto-fold with minimum loss (verify actual socket-disconnect handling in code — see Real-Time Architecture section — before relying on this behavior)

#### Roulette:
- Invalid bet type or amount → Show error, reset bet
- Connection lost during spin → Use server result for final outcome

#### Slot Machine:
- Insufficient chips → Block spin, alert user
- Multi-line payout calculation errors → Use safe default, log error

#### Cosmetics / Store:
- Insufficient chips for purchase → Block purchase, show alert (`INSUFFICIENT_FUNDS_FOR_PURCHASE`)
- Duplicate purchase attempt → Block purchase, inform user item is already owned (`ITEM_ALREADY_OWNED`)

### Logging and Monitoring

#### Logging Requirements:
- Log all authentication attempts (success/failure)
- Log game start, moves, and round results
- Log balance changes with user ID and game ID
- Log API errors with full context
- Log user registrations and account updates

[INFO] GameStarted [userId: user-uuid] [gameId: game-uuid] [game: blackjack] [bet: 100] [initialBalance: 1000]

### Testing Protocols

#### Before Committing Code:
1. Run backend tests: `cd backend && npm test`
2. Run frontend tests: `cd frontend && ng test` (or `npm run test` — confirm the exact script name in `frontend/package.json`, as this may run in watch mode by default; use `ng test --watch=false` for a one-shot CI-style run)
3. Test game logic with sample bets and win scenarios
4. Test edge cases (max bet, insufficient chips, invalid moves)
5. Verify database operations don't corrupt data — run against the isolated test database only (see Data Sources)
6. Check that API responses match expected formats
7. For accessibility-related changes, additionally run an AXE check against the affected components (see Accessibility standards above)

#### Test Data:
- Create test users with various balances
- Create test game states (incomplete rounds, completed rounds)
- Use small bet amounts for testing to avoid draining balances
- Clear test data after testing or use isolated test databases

## Agent-Specific Guidelines

### When Working with User Accounts:
1. Always check existing users first before creating new ones
2. Use default test credentials or prompt user for credentials
3. Never modify real user balances directly
4. Log all balance changes with user ID

### When Implementing Games:
1. Follow patterns from existing game code (blackjack.ts, poker.ts, roulette.ts, slotmachine.ts)
2. Implement both backend logic and frontend UI when needed
3. Ensure fair random number generation (not predictable)
4. Verify all game rules match user expectations
5. Test wins, losses, and edge cases

### When Working with Chat / Social Features:
1. Treat all chat input as untrusted user-generated content — sanitize before storage and before rendering
2. Check for existing profanity/content filtering in `backend/src/services/` before assuming none exists; if none exists and the task touches chat, flag this gap to the user rather than silently shipping an unmoderated public chat feature
3. Consider basic abuse-prevention (e.g., message rate limiting per user) when implementing or modifying chat endpoints
4. Do not log full chat message contents alongside personally identifying information beyond what's already logged elsewhere, to limit exposure if logs are compromised

### When Writing Tests:
1. Use TypeScript test framework (Jest or similar — confirm actual framework in `package.json`/`jest.config` before assuming)
2. Test both happy paths and error scenarios
3. Mock external dependencies if needed (e.g., database)
4. Keep tests isolated and fast
5. Ensure test data doesn't interfere with production — use the isolated test database, never `backend/resources/db.db`

### When Updating Documentation:
1. Match existing documentation style and format
2. Keep examples accurate and up-to-date
3. Document new features as they are implemented
4. Update API docs when changing endpoints
5. **Keep mirrored docs in sync**: `frontend/CLAUDE.md` is mirrored in `frontend/GEMINI.md` and `frontend/.github/copilot-instructions.md`. If you edit one, apply the same edit to the other two in the same change set — do not leave them to drift. If exact mirroring isn't feasible for a given edit, note in the commit/PR description which mirrored files were and weren't updated, and why.

### When Refactoring Code:
1. Follow existing code patterns and conventions
2. Maintain backward compatibility where possible
3. Update tests when changing existing functionality
4. Document any breaking changes
5. Get user approval for significant refactors

### Security Best Practices:
1. Always hash passwords with bcrypt before storage
2. Validate all inputs (never trust client-side data)
3. Sanitize user input to prevent XSS
4. Use prepared statements for database queries
5. Implement rate limiting for API endpoints *(not yet implemented in dependencies — see note under Backend Technologies; flag rather than assume when working near auth or betting endpoints)*
6. Never log or display full error stack traces to users
7. Use HTTPS in production (not currently implemented, but note for future — treat as a known, tracked gap rather than a currently-enforced control)
